# Trial: established refactoring and verification tools in place of custom proof tools (task 2q-r1, 2026-10-08)

**Scope:** a one-slice trial of the approach in `refactor-verification-20261008.md`, authorised by the operator on 2026-10-08. No production change. Evidence: `~/work/research-loops-public/private/evidence/2q-r1/` (`README.txt` there lists every file and its command).

## Result in brief
- **Trial A (rope + detector on the 2q-b9 `_write_evidence` split): partly worked.** Rope reproduced the five-helper extraction in 1.2 s, but its raw output is **broken**: it gave `_promote_and_link_claims` a spurious parameter `row` that the caller never binds, so 171 tests error with `NameError` and 4 more fail (175 of the 193 in the six modules run; the 4 are crash tests whose child process exits 1 instead of being killed, 137, for the same reason). With only that parameter removed by hand, rope's output equals the coder's `d649d51` apart from type annotations and the order of some parameters, and all 193 tests pass. The detector (RefactoringMiner on a pinned image) reported exactly the five Extract Methods, plus three refactorings of the move tool itself that the range also contains. It describes the change; it does not check it (it reported the five Extract Methods for rope's broken output too).
- **Trial B (Hypothesis `old == new` on the 2q-b4 decoder): worked.** 100,000 generated cases (seed 20261008, 360 s) and a second 50,000 (seed 7, 185 s) found no difference between the decoder before and after 2q-b4. All 17 behaviour-changing alterations of the new decoder were caught, each within 1,535 test calls (shrinking included) and 5.6 s; the 2 behaviour-preserving ones were not flagged in 20,000 cases each. It is the cheapest and clearest result of the three.
- **Trial C (time-machine + seeded fixtures on UNRESOLVED replay scenarios): partly worked.** In the process that runs the test, the libraries fix the clock and the ids. They do **not** reach a child interpreter at all. They reach one only if the child arms them itself, which needs an overlay and a `sitecustomize` (the same mechanism 2q-t4 built), and then every child draws the same ids. They do nothing for the real job-process identity (pid, start time, session), which is the cause of 349 of the 352 UNRESOLVED tests. A nine-line stdlib mock of the one fingerprint function did that part. With those pieces, two UNRESOLVED scenarios became deterministic over 4 runs each; I did not put them into the replay recorder, so no replay verdict was produced.
- **Recommendation:** adopt rope, Hypothesis and the detector for the remaining refactors, **with the test suite as the gate on rope's output**, and drop the 2q-b9b checker fix. Do not adopt time-machine as the answer to the 352; it replaces only the easy half of 2q-t4. Details in "Recommended workflow".

## Trial A: the `_write_evidence` split (base `08a1c1b`, coder `d649d51`)
**Method.** Rope's `ExtractMethod` driven programmatically on a copy of the `08a1c1b` tree (`trial-a/trial_a_rope.py`, 48 lines). The five blocks are found by AST (the same line ranges as the 2q-b9 README) and extracted bottom-up so that the helpers land in block order. No hand edit.

**It needed one setting.** The first attempt died inside rope (`ModuleNotFoundError: Module service not found`): `gen2/` has no `__init__.py` files, so rope names the module `service` and cannot resolve it. `Project(..., source_folders=["gen2/router"])` fixes it.

**Result.** Five extractions in 1.22 s (0.20–0.30 s each); a second run is byte-identical. Compared with `d649d51`'s `service.py`, AST-normalised in four steps (`trial-a/trial_a_compare.py`; the comparison of `d649d51` with itself is identical at every level):
- exact: the Router class differs in 6 methods;
- without annotations: 4 (the coder added `payload: dict` … `-> list` to every helper; rope adds none): **annotation difference**, no behaviour;
- also without parameter order: 2. Rope orders parameters by first use in the block, the coder in a fixed order: `_write_source_proposals(payload, inv, topic_id, op_id, now)` against `(payload, topic_id, inv, op_id, now)`, `_close_review_episodes(payload, topic_id, inv, now, op_id)` against `(payload, topic_id, inv, op_id, now)`, and the calls are generated to match. **Order difference only**;
- what remains: `_promote_and_link_claims` has an extra parameter, `row`, and its call passes `row`. **A real difference, and a fault** (below).
The helper order in the file, the module-level code outside `Router`, and the other 96 methods are identical.

**The fault.** `row` is assigned only inside the promotions loop, so in `_write_evidence` the name is unbound at the call: the module has no global of that name, so every commit raises `NameError`. Measured on a copy of `d649d51` whose `service.py` is replaced by rope's output, over `test_router_workflow`, `_evidence`, `_commit`, `_evidence_wiring`, `_crash`, `_lifecycle`:
- `d649d51`: 193 tests, all pass (19.6 s);
- rope raw: 171 errors and 4 failures; the output holds 174 `NameError: name 'row' is not defined` traces, and the 4 failures are `test_router_crash.KilledProcessTest` cases that expect the child to be killed (exit 137) and find it exited 1;
- rope with only `, row` removed from the signature and the call: 193 pass (19.4 s).
**Cause, from rope's source, with a bisected reproduction.** A smaller case reproduces it (`trial-a/rope_row_repro.py`, rope 1.15.0): the spurious parameter appears when (a) a comprehension earlier in the function binds the same name that the loop body later assigns and (b) the loop body has a nested `if` before the later read of it. Neither alone does. My reading of `rope/refactor/extract.py`: `_comp_exp` restores `read`/`written`/`maybe_written` but not `prewritten`, so the comprehension's `row` counts as defined before the region, and `_handle_conditional_context` sets `conditional` back to `False` on exit instead of restoring its previous value, so reads after a nested `if` in a loop count as unconditional reads. I confirmed the two conditions by bisection; I did not trace the failing path in a debugger.

**The detector** (`rm/wrapper-run.txt`; 5.7 s for the range including the JVM start): over `08a1c1b..d649d51` it reported 8 refactorings in 4 commits:
- the five Extract Methods, in `ad7d4c9`, with the coder's helper names and signatures and the call sites in `_write_evidence`;
- in the same commit, an Extract Method (`without_docstring` out of `dump`) and a Merge Conditional in `tools/gen2_move_equivalence.py`; in `fa4e2b2`, an Extract Variable (`matched`) in the same file. I read the diff of that file: all three are real edits of the inline-back tool, which the range also contains. Nothing is unexplained; the wrapper's `--expect "Extract Method=6" --expect "Merge Conditional=1" --expect "Extract Variable=1"` passes, and `--expect "Extract Method=5"` alone fails, naming all three extras.
- `08a1c1b` (the start commit is included) and `d649d51`: none.
**What it does not do** (three runs, `trial-a/detector-*.txt`): on rope's broken output it reports the same five Extract Methods, with `row` visible in one signature and nothing flagged; on the coder's whole extraction with one character changed inside the extracted helper (`+ 1` → `+ 2`) it still reports five; a bare one-character edit with no extraction reports none, which is right. So the detector gives a reviewer the list of what moved and where; it cannot catch a wrong extraction. The tests did.

**Verdict for A: partly.** The detector worked as a description. Rope saved the typing and produced the right shape, but it cannot be trusted without the tests, and the tests are what found its fault in 19 s.

## Trial B: Hypothesis differential on the 2q-b4 decoder (`_decode`, `3129cd5` → `8a59308`)
**Method.** `trial-b/differential.py` (207 lines). The old `core/schema.py` is a `git show 3129cd5:` copy loaded as a sibling module of the new one from `git archive 8a59308 gateway`, so both share `payload.py` (the same `PayloadError`, `Rec`, `MemberList`, `Unreadable`). Hypothesis draws a schema description (every constructor of the module: the nine leaf kinds, `soft`/`isolated`/`maybe`/`oneof`, `obj` with a rule that returns, raises or divides by zero, `own`/`members` with `bare`/`at_most`/`empty_when`, `grid`, `entries`/`table`, `lookup`, `matching`/`deep`/`by` as fields, `required`/`never_null`/`in_ns`, and a kind no table names) and a value shaped to it most of the time and junk otherwise (Unicode digits, a 5,000-digit string, NaN/inf, huge ints, XML elements). Both decoders get the same value object. The property is that `old._decode(spec, value, ())` and `new._decode(spec, value, ())` have the same outcome: the same canonicalised result (through the private slots of `Rec`, `MemberList`, `Unreadable`, `Passive`, order kept) or the same exception (type, args, cause and suppression), and neither changed its input.

**Result.** **No difference found** in 100,000 test-function calls (`max_examples=100000`, seed 20261008, 360.4 s, about 280 cases a second) and in 50,000 more with seed 7 (184.7 s). Outcome mix of the old decoder over the 100,000: 55,601 decoded results, 42,875 `PayloadError`, 1,373 `UndeclaredRead` (a rule reading an undeclared field), 151 `ValueError` (the unknown-kind refusal). So both the success and the failure channel are exercised, and the messages are compared whole. Line coverage of the decoder section (`_decode` to `_empty`, stdlib `trace`, a 15,000-case run with the same seed) is **100%: 226 of 226 executable lines in the old module and 236 of 236 in the new** (`trial-b/coverage-15000.txt`). A 6,000-case run had reached 98.3%, so the last four lines need a long run. Line coverage is not path coverage.

Two things went wrong on the way and are worth knowing. (1) The first run reported a "difference" that was my harness: `year_value`'s message embeds `repr(value)`, which for an XML element includes its memory address, and I had passed deep copies; both decoders now get the same object and the harness checks that neither changed it. (2) Measuring coverage showed my first generator never reached `deep`/`matching` fields, `empty_when`, or the unknown-kind refusal (the field-only kinds were drawn too rarely); I changed the generator and measured again. A differential whose generator has not been measured can pass for the wrong reason.

**Negative controls** (`trial-b/mutants/`, 19 altered copies of the NEW decoder, each edit text checked to occur exactly once): the nine dispatch mutants of 2q-b4 (`K-*`, written for a different purpose), eight edits of mine (several message-only or Unicode-edge), and two edits that change no behaviour. Result (`trial-b/negative-controls.txt`): **17 of the 17 behaviour-changing alterations caught, the 2 behaviour-preserving ones not flagged** (20,000 cases each, 75 s each).
- the nine `K-*` mutants: caught after 2, 9, 39, 40, 34, 65, 100, 147 and 148 cases (the call number of the first difference), 26 to 607 calls and 0.1 to 2.6 s in all;
- my eight: caught after 19, 246, 238, 248, 165, 734, 9 and 100 cases, including the three that change only an error message (`M2`, `M5`, `M8`) and the Unicode edge (`M7`, `isdigit` → `isdecimal`, caught at case 9); the slowest was `M6` (an unreadable member forgets what was sent), 734 cases, 5.6 s;
- `E1` (a local renamed) and `E2` (operands of an `or` swapped): no difference in 20,000 cases, as they should.
The first difference of each is printed in the file with both outcomes.

**Limits.** This reproduces one of the six drivers of the 2q-b4 evidence (the decoder alone, 19,385 runs); the other five compared whole adapter answers through the router (95,869 + 95,869 + 31,448 + 273 + 123 runs) and this does not replace them. The generator is mine, not the 2q-b4 battery, and its coverage claim is of lines, not of combinations of kinds. Hypothesis ran with `database=None` and a fixed seed, so each run is repeatable and a second seed was run to say the first was not luck.

## Trial C: determinism for UNRESOLVED replay scenarios (without the hand-built seam of `5ef2130`)
**Method.** `trial-c/run_scenario.py` runs one gen-2 test in a fresh interpreter per run, with chosen "parts" armed, and dumps every table of the test's store at the end (rows in insertion order). `compare_runs.py` lists the table.columns whose cells differ across 4 runs. The parts: `clock` = `time_machine.travel(fixed instant, tick=False)`; `rng` = a seeded `random.Random` behind `secrets.token_hex`/`token_bytes`/`token_urlsafe` and `uuid.uuid4` (`unittest.mock`), and `random.seed`; `fp` = `unittest.mock` of `gen2.supervisor.jobs.fingerprint` into the ordinal of the real fingerprint among those seen; `children` = a `GEN2_CHILD_ROOT` overlay (a link to the tree's `gen2/` plus a `sitecustomize`) that arms `clock` and `rng` in every child interpreter. Nothing from `tools/gen2_replay_seams.py` or `tools/gen2_replay.py` is used. Tree: HEAD (`0687a19`).

**Scenario S** (`test_station_config…StationSchedulingTest.test_a_mounted_fractional_hold_window_is_kept`; real job processes; UNRESOLVED on `start_fingerprint` and the fields derived from it):
- no part: **36 cells in 11 columns** differ between runs (ids: `audit_event_id`, `hold_id`, `lease_id`, `capability_id`; and the fingerprint-derived hashes);
- `clock,rng`: **12 cells in 5 columns**, exactly `invocations.start_fingerprint` and what embeds it (`artifacts.content_hash`, `artifact_topics.content_hash`, `invocation_transitions.facts`, `invocations.end_evidence_ref`): the real pid, start time and session, which no clock or random library controls;
- `clock,rng,fp`: **0**, deterministic. `children` changes nothing in S, in either combination: its children carry no value into the store.

**Scenario R** (`test_operator_restart…ReplacementTest.test_a_replacement_process_serves_the_same_principals_permissions_and_state`; real replacement engine processes; UNRESOLVED on `audit_events.at`/`audit_event_id` and `queue_entries.updated_at`):
- no part: 3 cells in 3 columns;
- `clock,rng` in the test process: **still 3 in 3**. Time-machine and the seeded fixtures **do not reach child interpreters**. Measured directly (`micro-demo.txt`): a child started under `travel` reads the real clock;
- `clock,rng,childrenpp` (the overlay through `PYTHONPATH`): every run errors, `ValueError: a gen-2 child imports from the code tree alone; this environment sets ['PYTHONPATH']`, the repository's own child-launch rule (`gen2/tests/children.py`). The existing route is `GEN2_CHILD_ROOT`;
- `clock,rng,children`: **0**, deterministic; 14 child interpreters were armed (3 engines, 11 CLI calls) and the test passed.

**What this does and does not show.**
- It shows the in-process half of 2q-t4's seam can be replaced by library calls (a frozen wall clock and seeded ids), and that the child half needs an overlay the libraries do not provide. The `sitecustomize` is six lines; the `GEN2_CHILD_ROOT` mechanism it rides on already exists.
- **Every armed child draws the same ids from the same seed** (`micro-demo.txt`: two children mint the identical `secrets.token_hex(4)`). It worked in R because only one child wrote an id; two engines writing audit events into one store would collide on `audit_event_id`. 2q-t4 counted ids across children for exactly this; the library approach has no answer except a counter shared between processes, which is hand-built again.
- The clock is frozen, not counting: all timestamps in a test are equal. 123 tests in four modules (`test_station_config`, `test_operator_restart`, `test_router_workflow`, `test_supervisor_requeue`) pass identically armed and unarmed (`frozen_clock_modules.txt`), so this did not bite here; `tick=True` would not be deterministic, and time-machine takes only the first value of a generator as a starting point, so it cannot count in milliseconds as the recorder does. It patches `time.time`, `time_ns`, `datetime.now`/`utcnow`, `gmtime`/`localtime`, `clock_gettime(REALTIME)`; it does not patch `monotonic`, `perf_counter`, `sleep` or file times (the supervisor's waits therefore still work).
- `fp` is a stdlib mock, not a library capability, and it is in-process: it works in S because the supervisor runs in the test process. Where a *child* supervisor computes the fingerprint, 2q-t4's file-shared ordinal is still needed. Not tried.
- Two scenarios of 352, compared on the final store contents of 4 runs each. I did not give the replay recorder these fixtures, so I did not produce a same/different replay verdict across two trees, and the per-call observations the recorder also compares were not compared.

**Verdict for C: partly.** Library calls cover the clock and ids of the test process cleanly and in fewer lines than hand-built patches. They do not cover children, process identity, or cross-process id uniqueness, which are the parts 2q-t4 found hard.

## Recommended workflow for the remaining refactors
1. **Perform** with rope where the move is extract-method or similar, `source_folders` set for the module's directory. **Treat its output as untrusted** (`trial_a_rope.py` and the comparison are the template). Check the signatures it produced against the caller's local names (the fault above is visible there) and run step 3 before anything else.
2. **Describe** with `tools/gen2_refactoring_detect.py START END --expect …`, with the counts the slice intends. It costs 6 s and replaces the move-equivalence and inline-back reports as the reviewer's map of the change. It does not replace step 3.
3. **Gate on behaviour** with the existing tests of the modules around the function (19 s found rope's fault), then the slice's mutation run as now. For a **pure function** (decoders, parsers, URL handling) add a Hypothesis `old == new` property with a negative control, as in Trial B; for the rest, golden-master assertions on the outputs that matter.
4. **Keep** the accepted 2q-b3b exact replay for Router-level slices as a final landing check; do not harden it further. Do not use time-machine to try to resolve the 352: it is good for the clock and ids of the test process only. Resolving the job-process identity needs a seam of 2q-t4's kind (or the stdlib mock, for an in-process supervisor), and children need the overlay.
5. **Astra reviews** the production diff and this evidence, as before.
6. **Drop 2q-b9b** (the inline-back checker grammar fix): the extract-method evidence it was to repair is now the detector's list plus the tests. This is the orchestrator's decision to take; the trial supports it for extract method on a function with test coverage like this one, and does not test it for moves between classes or files (the `EvidenceWriter` slice), which the detector covers in principle (Move Method, Extract Class) and which was not run here.

## Not tried or not shown
- PyRef; LibCST codemods; `crosshair diffbehavior`; `approvaltests`/`syrupy`.
- RefactoringMiner on a move between files or a class extraction (no such slice in this range). The detector's precision on Python is not established by one range; here all five extractions I expected were reported, and each of the 8 reports matches a real edit (I read the diffs); that says nothing about what it would miss.
- Rope on any refactoring other than extract-method; the rest of its fault surface.
- That the library fixtures would give the replay recorder a `same` verdict (Trial C compares end states only).
