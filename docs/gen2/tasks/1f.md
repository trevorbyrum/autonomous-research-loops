# Task 1f — Minimal deployment slice + the four auth-volume demonstrations (DEPLOYMENT-CONTRACT §4, pre-Phase-1 gate)

## Why this task
`docs/gen2/DEPLOYMENT-CONTRACT.md` §4 (~line 357) requires, **before Phase 1 is accepted**, that the deployment demonstrate with the pinned runner: (a) a credential refresh inside a live auth volume is picked up without a rebuild; (b) container replacement preserves auth-volume access and permissions; (c) concurrent use of one auth home by two simultaneous invocations behaves as specified rather than corrupting credential state; (d) a revoked or expired credential produces a dated capability fact and a typed capability hold, not a silent zero-result pass. The operator decided on 2026-09-28 to do this up front rather than amend the phasing. Astra's 1e review (finding 1) is the trigger; read its finding-1 section.

## Deliverables
1. **Minimal compose slice**, per the contract's shapes: the engine container (the existing `python -m gen2.app.engine`), mounted config bundle and env secrets, per the contract's baked-vs-mounted table; an **auth volume** mounted per §4 (fixed path, service uid/gid, 0700). No gateway, projector or research workflow — this is the smallest deployable slice that can run supervisor jobs. A pinned runner: pick ONE public provider CLI already on this host (`codex` or `claude`), pin its version in the image/volume per the contract, and record which and why. **Isolation is absolute:** own compose project name, own ports (only from the contract's defaults), own volumes under the repo or /tmp; never touch gen-1's services, containers, or any live credential store. Use throwaway/invalid credential files only — never the operator's real auth homes.
2. **A capability probe job** (supervisor-owned, per BOUNDARIES "capability probes"): a job the supervisor runs that invokes the pinned runner CLI against the mounted auth home in a no-network or trivially-failing mode chosen for determinism, classifies the outcome structurally (usable / unusable-credential / runner-error), and records it through the router as a dated capability fact; an unusable credential also opens a typed capability hold (H-2, RG-3). No research semantics, no live provider research calls, no billing-bearing requests: the probe must be designed so a revoked/invalid credential is detected from the CLI's own local behavior (auth handshake failure / explicit error), not by consuming quota.
3. **The four demonstrations, scripted and repeatable** (`deploy/demo/` + a make target, e.g. `make gen2-auth-demo`):
   - (a) refresh: swap the credential file contents in the live volume; the next probe picks up the new state without image rebuild or container recreation;
   - (b) replacement: `docker compose up` a replacement container; the auth volume's access and permissions survive, probe agrees;
   - (c) concurrency: two simultaneous probe invocations against one auth home; assert the credential files' bytes/permissions are uncorrupted after, and both invocations classify correctly;
   - (d) revoked/expired: an invalid credential produces a dated capability fact and a typed capability hold visible in operator status — never a silent success or empty pass.
   Each demonstration asserts its outcome mechanically (exit codes + store read-back + file checks), not by eyeballing logs. Keep full logs.
4. **Evidence report** `docs/gen2/AUTH-DEMO.md`: what was demonstrated, on what pinned versions, with links to the scripts; explicitly state what this does and does not prove (e.g., no live provider research call was made; the probe's classification of this CLI's failure modes is version-pinned).
5. **Contract corrections** if reality disagreed with the contract's text — as doc changes with the discrepancy named, or as findings in your report if normative.
