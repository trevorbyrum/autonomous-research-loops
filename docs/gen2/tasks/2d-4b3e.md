## Required
1. **Durable extraction record.** An immutable, append-only record of each extraction, with all of these:
   - its input, which is the consumed admitted acquisition (SQL 14);
   - the extractor's identity and version;
   - the invocation that performed the extraction;
   - the output bytes or their hash, staged as an artifact under the existing C-9 rules;
   - the tier the extraction's output actually supports, which can't exceed the recorded content ceiling.
2. **Durable validation record.**
   - It binds a specific extraction to an **independent** validator invocation. The producer can never validate its own extraction (role separation, as for verification).
   - It records the validation method and outcome.
   - Design the method set from the design authority. A deterministic re-extraction that reproduces the output hash from the same acquired bytes is one candidate; independent extraction is another.
   - The store binds recorded relationships only. Don't claim semantic correctness the store can't establish.
3. **Receipts consume these records.**
   - `validated_extraction` must reference a durable validation record whose outcome succeeded, and that is bound to the same acquisition, work, version and verifier lineage. That reference replaces the free-text `validation_ref` as the source of authority.
   - `verifier_extraction` must reference the verifier's own durable extraction record.
   - Invented, unbound or failed references are refused, whether they arrive through the Router or a raw insert.
4. **Replace the SQL 17 fence** only with consumption of these records.
   - A load-bearing `supports` from an extraction method can authorize support only when its durable basis exists and binds.
   - Everything else stays fenced.
   - Keep the missing-content hold behaviour, and keep SQL 12 and `EvidenceWriter` canonical-support consumers intact unless the design explicitly and soundly extends them.
5. **Tests.**
   - Router and raw-DDL tests for both methods:
     - a missing, unbound, foreign or failed extraction or validation;
     - a producer self-validating;
     - another work or acquisition;
     - an accepted control at each valid tier;
     - promotion through the replaced fence;
     - readback, replay/conflict and rollback.
   - Keep every negative isolated.
   - Add a predicate-level paired mutant for each guard.

## Operator ruling 2026-10-12 (Trevor): independent extraction
Answering the open question in DOSSIER §2d-4b3e.
- **Only an independent extraction can validate an extraction for load-bearing support.**
  - A separate validator invocation re-extracts from the same admitted acquisition bytes, using a **different extractor tool or method**.
  - It is never the producer's selected output.
  - The two outputs are compared.
  - The validator's independent output and its comparison evidence are kept.
- **Same-extractor deterministic replay** (an identical tool or version on identical bytes reproducing the output hash) is recorded only as an **integrity result**. It never grants support authority on its own, because it reproduces systematic extraction errors.
- **Basis:** the Cochrane Handbook recommends that at least two people extract data independently. This is also flow S4 step 8 and adjudication K-A2: "different URLs can still share one faulty extraction".
- **Implementation follows Sol's three-part split** in DOSSIER §2d-4b3e: records about 480 lines, then receipt consumption about 460, then replacing SQL 17 about 310. Re-estimate each at dispatch.

## Operator ruling 2026-10-14 (Trevor): extractor identity through a tool registry (settles N1)
- **An operator-maintained, versioned registry of approved extractor tools.** Each tool has a canonical identity and belongs to a **family**. For example, two parsers from the same codebase share a family.
- **Extraction records must name a registered tool.** Unknown, aliased or case/whitespace variants are refused at admission.
- **Independent validation** under `extraction-validation/1`'s successor policy requires a **different family** from the target extraction's tool. Same-family replay stays an integrity result only.
- **Registry changes are versioned and audited,** and are never caller-supplied in an outcome.
- **Later:** when the station runs extractors itself (2e2), the tool identity recorded at execution is checked against the same registry.
- **Basis:** Astra 2d-4b3e1 N1. Arbitrary unequal labels can't stand in for demonstrated method independence.

## Operator ruling 2026-10-15 (Trevor): the latest registry revision governs new validations
- **New `/2` validations must be compared under the registry revision that is current when the validation is admitted.**
- An operator reclassification takes effect immediately. A merge, for example two tools discovered to share code, can't be sidestepped by citing an older approved revision.
- **Validations already retained keep the interpretation they were recorded under.** Later registry changes never rewrite history.
- **Basis:** Astra 2d-4b3e2 p2 round 2 identified the validator-selectable revision as a trust boundary. "Revocation takes effect now" semantics.
