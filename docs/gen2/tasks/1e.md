## Build `gen2/operator/` + the transport in `gen2/app/`
One command service. Every command goes through the router's existing operations — the operator module gets no store access and no new write path.

1. **Authentication and authorization.**
   - Principals are authenticated by bearer token from the mounted secrets surface (the env names the deployment contract already defines). Constant-time comparison; tokens never logged or echoed; a missing/invalid token is refused before any parsing beyond what routing needs.
   - Authorization is per command class: privileged commands (decisions, config activation, brief closure, re-queue) require the operator principal; the projector's token authorizes only delivery acknowledgement; a capability-bearing call authorizes only its own invocation's operations. A principal or capability never substitutes for the other.
   - Auth configuration persists and survives restart (RG-9).
2. **Commands** (thin, over existing router operations): apply an operator decision (G-13 exact-subject rules already enforced by the router); request cancellation; clear a hold (the router already refuses clearing an episode hold without its reconciliation); activate a config bundle; brief versioning/closure/archival; propose/approve amendments; re-queue failed or cancelled work; acknowledge delivery (projector token only).
3. **Status (RG-9: why every waiting item waits).** One status surface that reports, per topic and per invocation: state, lease and generation, open holds with owner and deadline, incidents (including the collected-end one and retry exhaustion), `outcome_unknown` episodes and their reconciliation state, re-queue and reservation standing, amendment fencing (`amendment_pending` and what supersedes it), capability facts (bundle health included), and the active/pinned config bundles. Status is read-only and must not mutate anything.
4. **Health**: `/v1/health` unauthenticated, minimal, no state leak.
5. **CLI**: a thin client of the same API — no second code path.
