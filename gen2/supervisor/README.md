# Gen-2 station supervisor (task 1c)

`supervisor.Supervisor` is the one lifecycle implementation for every invocation kind: research pass, discovery, delegate, verification and checkpoint (BOUNDARIES.md *Station supervisor*; INVARIANTS RG-2). Nothing in it branches on the kind except the claim a delegate makes under its parent's capability (L-8) and, for a parent, ending its delegates before its own end. It reaches the router only through the `ControlBackend` protocol (`gen2/core/control.py`), wired by the composition root (`gen2/app/station.py`). It imports neither router nor store (`gen2/boundaries.toml`).

| File | What it is |
|---|---|
| `supervisor.py` | The lifecycle: `prepare`/`submit` an order, `advance` one step, `run` to an end, `recover` after a restart, `recover_incident` for the operator's recovery of one stalled job, `incidents` to list what is open. |
| `jobs.py` | A job per invocation under its stable handle `job-<invocation id>`: its directory, its journal lock, the launcher start, lookup by handle, process identity, the execution group and its termination. |
| `jobshim.py` | The launcher: a standard-library script started by path in its own session. It is the job's execution group, and it outlives the supervisor. |
| `spool.py` | The protected spool (C-9): immutable, content-addressed, topic-scoped and size-bounded. It is also the router's `StagedBytes`. |
| `fake_executor.py` | Deterministic, scriptable stand-ins for an agent of any kind: no model, gateway or network. |

## One job, three durable records

A supervisor holds nothing it needs only in memory. Each `advance` rebuilds its view from:
- **The job directory** (`jobs.py` docstring). It holds the order, written before the claim, and what the launcher recorded: `spawn.json` is written before each start, and `identity.json` and `exit.json` are written atomically by the launcher. It also holds the supervisor's `journal.json`, whose writers hold the job's `journal.lock` (*One caller at a time per job*, below). The journal holds the grant; an end being observed (`observing`) and the end observed and retained (`collected`); the request an end or a reconciliation sends, fixed with its staged record (`pending`); the envelope it sent; its budgets; an outage in progress; and its incidents.
- **The spool.** It holds the result bytes and every execution record (`execution-record/1`, `gen2/schema/execution-record.schema.json`).
- **The router.** It holds the authoritative lifecycle (L-1), read with `invocation_status`.

## The lifecycle

Each `advance` first observes the job **locally**. This needs no router, so admitted work finishes and is retained while the router is away (C-10):
- An exit is collected. The rest of the execution group is ended and confirmed gone (L-7). The output is checked structurally and staged. The execution record is written.
- At its deadline a live group is terminated: a running one, and one whose launcher has vanished while members of its session remain. This does not wait for a router answer (Astra 1c review A9).

What cannot be done twice is kept in the journal before the next step: the descendants handled, the observation with its staged result, a termination as it happened. A write that fails is retried from there; nothing is observed or signalled again for it.

Then it drives the router one step:

| Router state | What the supervisor does |
|---|---|
| `admitted` | Records launch intent before any start (L-2); the router checks launch admission (lease, pause, deadline, cancellation; L-7) as it records it. A paused topic is retried within the launch budget. After that, or on a lapsed lease or deadline, the supervisor cancels the admitted work itself (`requested_by: supervisor`); nothing was spawned. |
| `launching` | Before **every** actual start — the first, a start retried after the OS refused one, a start after a restart — reads the router's current launch-admission check (`launch_admission` in `invocation_status`): recorded launch intent is not renewed authority (A1). A withdrawn authority starts nothing: a pause waits within the launch budget, then (or for a lapsed, released or replaced lease) the work is cancelled. Otherwise it starts the launcher (spawn budget) and records the identity the launcher recorded: job handle, host, container, boot id, and a start fingerprint of pid, start time and session (L-3). A start this process did not see through enters `outcome_unknown` (`spawn_uncertain`). |
| `running` | Delivers the collected end: a structural finding is `failed` with its class and record, and a clean end is `result_ready`. A cancellation request terminates the group, then records `cancelled` once descendants are confirmed. A launcher gone with no exit record enters `outcome_unknown` (`contact_lost`). A group whose termination is unconfirmed enters `outcome_unknown` (`termination_unconfirmed`) and releases no capacity. |
| `result_ready` | `commit_outcome` of the retained result, with its execution record as a result reference. A stale state revision or a paused topic is re-sent within the commit budget. Any other refusal is `failed` (`result_rejected`), and the result stays in the spool, uncommitted. |
| `outcome_unknown` | Reconciles the current episode (L-4) with what the job's handle finds: `found_running` (a live, verified launcher), `found_result` (the collected clean result), `confirmed_failed` (a finding, a launcher gone with nothing left, or a start that never ran), or `terminated_group`. A terminated group ends `failed` with its failure class, or — when cancellation was requested — `cancelled` with none: no failure class is invented for a cancellation (A2). For work that already exited, the cancellation is reconciled by the same idempotent group termination, which on an empty group signals nothing (recorded as `none_found`), and the exit stays as the launcher recorded it. What cannot be established stays unknown under the episode's router hold, which has an owner and a deadline and clears only through the episode's reconciliation (A7). |

**Structural checks decide (L-5, L-9).** The executor's result is one file of its scratch directory, `outcome.json`; the supervisor chose that name. Each of these is a failure with a structural class:
- a non-zero exit (`exit_nonzero`) or a signal (`killed`);
- a missing or empty file (`empty_output`), whatever `status.json` says;
- a symlink, hard link, special file, oversized file, or a file that changed while it was read (`output_refused`; A10);
- a declared digest the bytes do not have (`output_digest_mismatch`).

The agent's self-report is recorded as data and decides nothing. The declared digest is checked data that cannot establish success: one that disagrees with the bytes refuses the output, and one that agrees adds nothing — the supervisor's own hash of the bytes is what is recorded. Empty output is written to the store as the failed transition itself, with its class, its execution record (an artifact) and its audit event, never as a bare return code.

**Capacity (L-7, L-8).** A failure or cancellation releases the lease only when its execution record confirms the descendants were handled; the router refuses the end otherwise. A parent's lease is also its delegates', and a delegate runs in its own session, which the parent's descendant check cannot see: before anything that releases a parent's capacity (a failure, a cancellation, a terminal reconciliation, an unlaunched end, the final commit), the supervisor ends every delegate job it holds for the parent — cancellation requested, group terminated, or an already staged result delivered — and the parent waits until the router confirms each ended. The router refuses the parent's release while a delegate is live (A3).

**Policy from the pinned bundle (task 1d; G-10, RG-9).** `Policy`'s values are the shipped defaults; a config bundle's supervisor section overrides them value by value (`supervisor_policy`). Every production start of the composition root (`open_station`) installs the resolver (Astra 1d review finding 2): each job's budgets, windows and graces are those of the bundle its order is pinned to — the bundle it was admitted under — resolved the same way after a restart onto a newer bundle, or with nothing mounted, so a mounted edit applies to the next admission only; an order pinning no recorded bundle is refused before anything is written. The station's own values (the lock wait, polling) are the mounted bundle's, or with none mounted the active one's (the persisted configuration, which the router restores, recording recovery from a refused mount); with neither, the station does not start. Without a resolver — the supervisor built directly, or `open_station(fixture_policy=...)`, a test fixture outside that guarantee — one `Policy` is every job's.

**Re-queues and reservations (task 1d-repair; Astra 1d review finding 3).** A `WorkOrder` may name `retry_of`, the lane's ended work it re-runs as its re-queued retry, and `reservation` (`{reservation_id, facet_id?}`), the reservation its admission draws on. Both are stored with the order and sent with every claim of it, so a restart before the claim or a lost reply sends the same request and the router replays it. The router judges them (the lane gate, the budget, the draw); a delegate's order naming either is refused (`not_admitted`: a delegate holds its parent's lease). Nothing here re-queues on its own: the re-queue is the router's `requeue`, asked for by the operator or a policy caller (`gen2/tests/test_supervisor_requeue.py`).

**Budgets and incidents (L-6, RG-3).** Every retry path draws on a budget in the job's `Policy`, kept in the journal before each attempt, so a restart does not refill it. A retry is a resend of something that failed or was refused; reading a status while waiting (on a running job, or a parent on its delegates) is not one (see *Waiting is not retrying*):
- *Router.* An outage is budgeted from its first failed call until a write the router answers; a successful read refunds nothing (A5). It is bounded by attempts (`router_attempts`) and by time (`router_window_s`). Past either, the job stalls with a `router_unreachable` incident.
- *Durable writes.* A write the supervisor cannot make — a record or result over the spool quota, a file-system error from the spool — is an infrastructure failure, never a completion (C-10). It is retried on later advances within `write_attempts`; past that the job stalls with a `durable_write_failed` incident naming its phase and error. A write failing while the job is already stalled on another incident (a termination record staged at the deadline while the router is away) is retried within the same budget and then waits for `recover()` too; the incident the job stalled on stays as raised. When the journal itself cannot be written, the incident cannot be kept either: `advance()` raises `ControlFailure` to its caller, out of band, and `recover()` raises it after trying every job (A4).
- *Refused lifecycle writes.* An end, a reconciliation, entering `outcome_unknown` or a cancellation (the supervisor's own, or a delegate's that its parent asks for) that the router refuses is decided and sent afresh on a later advance within `refusal_attempts`; only that write's acceptance refunds it. A refusal no retry can change — a conflicting recorded fact (`transition_conflict`, `reconciliation_conflict`, `cancel_conflict`) or a capability the router does not know for the invocation — stops at once. Either way the job then stalls with a `lifecycle_write_refused` incident naming the budget, the write and the last refusal.
- *Unresolved `outcome_unknown`.* An episode that cannot be reconciled yet — a termination not confirmed, a start still unresolved after its grace, a launcher that took the lock before the start could be abandoned — is looked at again on a later advance within `unknown_attempts` and `unknown_window_s` (from its first unresolved look), counted per episode and refunded by its reconciliation. Past either, the job stalls with an `outcome_unknown_unresolved` incident naming the episode and what was last found; nothing is reconciled, so the episode's hold stays with the router (L-4).
- *Recovery.* `recover()` resumes a stalled job, drawing on `recovery_attempts`. It does not refill the budget that ran out: a resumption that fails again stalls again at once. `recover_incident()` is the operator's recovery of one job, on the same budget (task 1e-repair; Astra 1e review finding 2, carrying the 1c re-review 2 escalation): where the retained end's descendants were never confirmed ended — the collected end, which `recover()` alone finds again unconfirmed and stalls on — it first ends the job's owned group afresh and keeps what that found beside the retained end (`collected.rehandled`), the retained observation and record unchanged; still unconfirmed, the incident stays open and nothing is released. Then the incident closes and the job advances: the `outcome_unknown` episode is reconciled by the router from a fresh execution record of that handling (`_unknown` reads `rehandled`), the only way its hold clears, capacity released only then. Keyed by the incident; its attempts are kept in the journal (`recoveries`). `gen2/operator/README.md` describes the route that calls it.
- *Launch, spawn and commit.* When one of these retry budgets runs out, the job ends as before (cancelled, `spawn_failed`, `result_rejected`) and a `retry_exhausted` incident is recorded beside that end, with the budget, the last refusal and the result it concerns (A11). An ordinary resolved failure, or a refusal that is not retried, raises none.

Every incident has an owner (`supervisor:<station>`) and a deadline (`incident_window_s`), and `Supervisor.incidents()` lists them, each with its invocation and its topic from the job's durable order (Astra 1e review finding 5). The one a stalled job waits on is cleared by `recover()` or the operator's `recover_incident()`; a `retry_exhausted` incident is a record for the operator: the operator surface's status lists every open incident and names it on its invocation or topic (task 1e, `gen2/operator/README.md`).

**One chokepoint for every router call (task 1c-repair-3; Astra 1c re-review 2, L-6).** Every control call goes through `Supervisor._call()`. It makes none for a job stalled on an open incident, or settled — as that job's own durable journal says, whatever job or journal copy the caller holds — whoever calls: the job's own advance, its parent ending it (A5-R), its delegate needing its capability (the recursive grant Astra reproduced for all four parent kinds), or `recover()` with no recovery attempt left. The refusal writes nothing: the incident stays as raised and the spent budget stays spent until `recover()`, drawing on the recovery budget, closes the incident. A delegate whose parent is stalled waits (`parent_stalled`) and sends nothing; a delegate whose parent ended `not_admitted` is not admitted either, and the parent is never claimed again (a second claim could admit work no job will run, holding a lease). An open incident is write-once: `_incident()` keeps one already open in the durable journal — kind, since and deadline — whatever copy its caller holds. With the chokepoint and the write gate above, no current path reaches the writer while an incident is open; the write-once rule is the backstop for a future one, tested directly with a stale copy and with the current one (it writes nothing; a stale copy's write would also be refused by the journal's revision check, below). While a job is stalled its deadline is still enforced locally (no router needed), and explicit `recover()` still resumes it.

**One caller at a time per job (task 1c-repair-4; Astra 1c re-review 3, BLOCK 1).** Astra reproduced a lost update: an advance that had read its job's journal before another advance exhausted the router budget and opened an incident later saved its older copy over both — the incident erased, the router budget back at one, twelve failing calls where six are allowed — for every parent kind, with one supervisor shared by two threads and with two supervisors sharing the jobs directory. Now:
- `advance()`, and each job's step of `recover()` (its resumption and its advance), hold the job's lock from the read of its journal to its last write. The lock is an open-file-description write lock on the job's `journal.lock` (`jobs.Job.hold`): one holder at a time across the processes and threads of the host, released by the kernel when its holder lets go or dies, so a crashed holder wedges nothing.
- A delegate's advance takes its **parent's** lock first, then its own: its grant claims the parent's capability, writing the parent's journal. A parent ending its delegates takes each delegate's lock under its own. Every caller takes them in that one order, parent before delegate, so no two wait on each other; a caller that already holds a lock (a parent advancing its delegate, `recover()` advancing its job) takes it again at once.
- Waiting for a lock is not a retry: it spends no budget, and it is bounded (`lock_wait_s`, the last try made at that bound); past it the answer is `busy`, with the journal neither read nor written and nothing sent. (A delegate's lock, taken inside its parent's step, is held by no other caller at that moment: every holder of it took the parent's first.)
- As a backstop, the journal carries a revision: a write resting on a copy older than the durable journal is refused (`StaleJournal`, a `ControlFailure`, out of band) and nothing is written. The check and the write are two steps, so this is not a lock: a caller that does not take the lock can still make its one extra call, but cannot save its older copy over the incident.

So no caller reads a journal another is changing, and none writes an older copy over a newer one: every read-modify-write of a job's journal is one caller's. The budget and incident claims above — spent budgets stay spent, an open incident is kept as raised until `recover()` closes it, each retry path is bounded — therefore hold for overlapping callers on one host, threads of one supervisor or supervisors sharing the jobs directory, as they do for sequential ones. The scope and limits of the lock: **per job** (plus its parent, for a delegate); **across processes on one host**; **nothing is claimed across hosts** — whether another host's lock on a shared file system is seen depends on that file system, and none is tested; there, only the backstop is relied on, and it does not stop a call.

**Waiting is not retrying.** Each `advance()` is one step, and `run()` is bounded by its timeout. A parent waiting on its delegates retries nothing of its own: each advance reads its status and advances each delegate, whose own budgets apply, so a stalled delegate holds its parent at that delegate's incident. Waiting for a job's lock is not a retry either (above).

**Crash and restart.** The launcher runs in its own session and survives the supervisor. `recover()` advances every job from its handle. A start found after a restart gets `start_grace_s` to show itself. Before a start that left no identity is settled as never started, the supervisor marks the job `abandoned` and then asks whether a launcher holds the job's lock. A lookup only asks (an open-file-description lock query) and never takes the lock, so it cannot make a launcher that is locking at that moment give up (task 1c-repair C2: that race ended jobs as never started under load). A launcher that takes the lock after the mark reads it and starts nothing (`jobshim.py` steps 1–3). So "never started" is final. The request of an end or a reconciliation is fixed with its staged record before it is sent, so a retry after a lost reply sends the identical request and replays.

## What is proven, and where

- `gen2/tests/test_supervisor_lifecycle.py`: the fault set for all five kinds, with real child processes. It covers a clean end; empty output, including a claimed success without output; a wrong declared digest; a symlink or hard-link output; an exit code or signal; a live descendant after exit; timeout; cancellation, and cancellation racing completion in both orders; pause at launch; a retried start admitted again; a stale result after lease loss; replay of a delivered result; router outage and recovery, including a deadline passing during the outage and a launcher that vanished during it; `outcome_unknown` entered and reconciled, both by termination and by lookup; and the launch, spawn and commit budgets with their exhaustion incidents.
- `gen2/tests/test_supervisor_crash.py`: the supervisor killed with `os._exit` at each lifecycle boundary and restarted, for all five kinds. This includes a crash between spawn and identity record, a second crash right after entering `outcome_unknown`, a recovery after launch intent whose authority was withdrawn meanwhile (pause, expired, released or replaced lease, cancellation; a delegate's replaced lease under each parent kind whose lease can be replaced, beside the unchanged-authority control), and cancellation after an uncertain spawn (live, exited, never started); and, beside the start that never happened, the alternative its abandonment guard admits: starts the OS refused leave nothing to abandon, and an `outcome_unknown` episode over them (seeded through the router's operation) is reconciled as never started with no abandoned mark (Astra 1c re-review 3, BLOCK 2).
- `gen2/tests/test_supervisor_delegates.py`: the four parent kinds ending — completion, failure, cancellation, a vanished launcher's reconciliation, a start that never happened, a supervisor restart — with nothing of the delegate's group alive at any releasing call; and a delegate stalled on a partial outage (its status read, or its cancellation), where a restarted supervisor's parent advances make none of its calls and leave its incident and the store unchanged, its deadline still ends its group, and recovery ends it and then the parent. The chokepoint, for each parent kind: a parent stalled on its claim is claimed again by no caller (its own advance, its delegate's advances after a restart — Astra's reproduction — another job holding a stale copy of its journal, for every control method, and `recover()` once no recovery attempt is left), its incident, budgets and the store unchanged, and recovery then starts the parent and its delegate; the same callers, and the parent ending it, for a stalled delegate; and a parent that ended `not_admitted` is not claimed again for its delegate.
- `gen2/tests/test_supervisor_budgets.py`: durable-write failures (record over quota, ENOSPC, termination and reconciliation records, an unwritable journal, a termination record failing while the job is stalled on an outage), partial router availability, a refused lifecycle write (retried within its budget, a conflict stopping at once) and an `outcome_unknown` episode that cannot be reconciled (by attempts and by time, its hold kept), for all five kinds, each with a restart that preserves the incident and a control that recovers within budget or through `recover()`.
- `gen2/tests/test_supervisor_serialization.py`: the per-job lock, for each parent kind. Astra's overlapping-advance regression, with one supervisor shared by two threads and with two supervisors sharing the jobs directory, the first advance paused in the chokepoint (her schedule) or just after its snapshot read: the other advances wait and send nothing meanwhile; then six calls in all, the router budget at five, the incident kept with its deadline, and half an hour later nothing more sent. Two overlapping `recover()` calls are two recovery attempts. Waiting is bounded and spends nothing (`busy`). A caller not taking the lock cannot save over the incident (the backstop), though its one call is made. A parent ending and its unclaimed delegate's grant, in both orders: each completes (no deadlock), the delegate cancelled and ended, the parent failed. Once: a write resting on an older copy is refused, and a supervisor process killed while holding a job's lock leaves it free — busy while it lives, the next advance proceeding once it is dead.
- `gen2/tests/test_supervisor_spool.py` and `test_supervisor_jobs.py`: the spool's and the job layer's own guards, including a scratch file changed while it is read and the lock probe.

The tests are chosen schedules. What carries the claims to every schedule on one host is the lock: with each read-modify-write of a job's journal one caller's, overlapping callers act as some sequence of them, which the tests above cover; the serialization tests show the exclusion and the lock order themselves.

## Structural limits

- Faults are what these processes can do to each other on one host: kills, exits, hangs and lost replies. They do not cover power loss or disk corruption; a kill leaves the page cache.
- Fencing protects commits. It does not undo an orphan's external effects (L-7).
- A descendant that leaves the job's session (`setsid`) is not seen or ended. A pid reused by a new session leader within a job's life would be counted as a member. Members are listed (session, start time, not a zombie) and then signalled by pid: in the interval between listing a pid and signalling it, it can exit and be reused by an unrelated process, which would receive the signal.
- The spool and job directories are protected by being the station's, not by the OS: another process of the same user can write them. Isolation is deployment's (1e authenticates the operator surface; it does not isolate the station's files). A scratch change that leaves a file's size and times as they were (within one timestamp tick of the previous write) is not detected; the job's group is ended before collection, so it needs a process outside the group.
- The spool's aggregate quota is counted per `Spool` instance, from its own writes and its last listing: two instances writing one root can exceed it together. One writer per spool root is a deployment restriction.
- The supervisor trusts its own observations. The router binds the execution record to the invocation, the job and what the record supports, not to whether it is true.
- The job's lock is per job and per host. Supervisors on different hosts sharing a jobs directory are not known to be excluded (whether the lock is seen there depends on the shared file system; nothing claims it); only the revision backstop is relied on between them, and it refuses the stale write without stopping the call. Deploy one host per jobs directory.
- Linux only (`/proc`, open-file-description locks).
