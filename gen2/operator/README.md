# Gen-2 operator surface — one command service (task 1e)

The operator's commands and status, behind one service (`service.py`, design review §10: "CLI/MCP/API operations behind one command service"). The engine's HTTP listener (`gen2/app/engine.py`) carries it, and the CLI (`gen2/app/cli.py`) is a client of the same routes; neither decides anything. Every command is one of the router's existing operations, called through `core.control.OperatorBackend` — but two, the station's: `recover_incident`, the recovery of a stalled job (below), which reaches the router only through the invocation's own capability-bearing operations; and `probe_capability` (task 1f), a probe of one provider's auth home with its pinned runner, whose observation the router records (`record_capability_probe`). This module imports only `core`, holds no store and has no write path of its own, and has no network capability (`gen2/boundaries.toml`; the transports are the composition root's).

| File | What it is |
|---|---|
| `auth.py` | Principals from the mounted secrets, and bearer-token authentication. |
| `service.py` | The routes, the checks in order, authorization per command class, and who acts. |
| `status.py` | Why every waiting item waits, composed from the router's status read and the station's incidents. |

## Principals (`auth.py`; DEPLOYMENT-CONTRACT.md §1.1, §3.1)

- Each `GEN2_OPERATOR_TOKENS` entry (`name=token`, comma-separated) is an operator named by its entry; `GEN2_SECRET_EXPORTER_TOKEN`, when set, is the principal `exporter`. `GEN2_SECRETS` must be `env` (vault waits for §3.4). The engine does not start without an operator token, with a token shorter than 16 characters or not visible ASCII, with a name twice, or with two principals sharing a token; no refusal names a token.
- A presented `Bearer` token is compared in constant time: its SHA-256 digest against every configured digest with `hmac.compare_digest`, all of them, no early exit, so which principal matched does not change the work (the presented token's length does: SHA-256 reads all of it). Tokens stay in `auth.py`: never logged, echoed, returned or stored; the configured ones are kept in memory there only for `redact()`, which takes each out of whatever the listener writes (below).
- **Persistence (RG-9).** The principal set is the mount's, read at every start: a restart or a replacement with the same mount keeps each principal, its role and its permissions; a token rotated out of the mount stops authenticating at the next start. That is how an env token expires (DEPLOYMENT-CONTRACT.md §2: env secrets change by restart); env tokens carry no expiry of their own.

## Routes and checks (`service.py`)

`GET /v1/health`, `GET /v1/status[?topic=<topic_id>]`, `POST /v1/commands/<operation>`, and `POST /mcp` (below). In order — a missing or invalid token is refused before anything but the route is read:

1. `GET /v1/health` needs no token and answers `{"status": "ok"}` (the router can take its store's write lock now) or 503 `{"status": "unavailable"}`, nothing else. Of DEPLOYMENT-CONTRACT.md §1.2's definition, the compatibility gate and the schema-identity check run when the store is opened (`gen2/store/db.py`; the engine does not start otherwise); the last scheduler tick has no scheduler to report until Phase 2.
2. The bearer token names a principal, or 401 (the same reply for every failure). The body is not read, whatever length it declares.
3. The route is status or a command, or 404; the principal's role is the one it needs, or 403 (over MCP the tool is in the body, so this follows step 4).
4. The body: a declared length (411 without, 413 over 1 MiB), strict JSON (C-13: duplicate keys and non-finite numbers refused), an object; 400 otherwise. Status's query is none or exactly one `topic` (a repeated or unknown key: 400); over MCP the whole envelope is checked first (below).
5. Who acts is the principal's, never the request's: a body naming `operator_id`, `requested_by`, `closed_by` or `capability_id` is refused (400 `authority_in_request`), and the others are set from the principal.
6. The router's operation answers (200), whatever it decided: `status` in its reply says what happened, a refusal included.

| Route (`<operation>`) | Role | Supplied from the principal | Router operation |
|---|---|---|---|
| `GET /v1/status` | operator | — | `status` (then `status.py`) |
| `apply_operator_decision` (decisions, hold clearance, amendment and reframe approval) | operator | `operator_id` = the operator's name | `apply_operator_decision` |
| `request_cancel` | operator | `requested_by` = `operator` | `request_cancel` |
| `requeue` | operator | `requested_by` = `operator` | `requeue` |
| `close_brief` | operator | `closed_by` = the operator's name | `close_brief` |
| `activate_config_bundle`, `version_brief`, `mark_brief_overdue`, `propose_amendment` | operator | — | the same |
| `recover_incident` | operator | `requested_by` = the operator's name | none: the station's `Supervisor.recover_incident`, which reaches the router through the invocation's capability (`reconcile` for an `outcome_unknown` episode) |
| `probe_capability` (task 1f) | operator | `requested_by` = the operator's name | none: the station's probe (`gen2/supervisor/probe.py`), `{"provider"}`; the router records its observation (`record_capability_probe`: the capability's dated fact on a transition, its operator hold when not usable). The engine runs the runner on the request's thread and only the record on the router's, so two probes run at once |
| `ack_delivery` | exporter | — | `ack_delivery` |

**Authorization per class.** Privileged commands need an operator; the exporter's token authorizes delivery acknowledgement only (no operator command, status included), and an operator's token does not acknowledge a delivery. **Capability-bearing calls** (claim, `record_transition`, `record_observation`, `commit_outcome`, `reconcile`, `invocation_status`, a supervisor's cancellation) are not routes here: the supervisor makes them in the engine's own process under the invocation's capability, and no principal the deployment contract defines holds invocation authority. So an operator's token cannot drive an invocation (404), and a capability — never a bearer token here (401), never accepted in a command body (400) — cannot issue an operator command. The Phase 3 exporter, which will run under an invocation, adds its capability-bearing calls needing both its token and that capability.

**MCP** (`POST /mcp`; DEPLOYMENT-CONTRACT.md §1.1: stateless MCP over HTTP, one JSON-RPC message per request, the gateway's shape). The same token and checks; `initialize` (answered with the protocol version asked for when the server supports it, its newest otherwise), `ping`, `tools/list` (the tools the principal's role may call: for an operator, `status` and the operator commands; for the exporter, `ack_delivery`) and `tools/call`, which runs the same `_status`/`_command` the routes run, so it is a transport and not a second path. No dependency: JSON-RPC over the same listener.
- *The envelope, whole, before anything is dispatched* (Astra 1e review finding 4): members only `jsonrpc`, `id`, `method`, `params`; `jsonrpc` exactly `"2.0"`; `method` a string; `id` a string or an integer, never null, a float, a boolean or a structure; `params` an object — otherwise -32600 Invalid Request. Each method's params carry only its own members, each of its type, the required ones present (`initialize`: `protocolVersion`; `tools/call`: `name`, and `arguments`, which omitted is `{}` and given must be an object — `[]` or `null` is refused, never read as `{}`) — otherwise -32602 Invalid params. Both are HTTP 400 with the command path's own refusal (`{"status": "refused", "reason": "request_invalid"}`) as their `data`, and nothing is dispatched. A message without an `id` is a notification: a `notifications/` method is 202 and does nothing; any other method needs its id (-32600).
- *A well-formed call's refusal*, at any later step — the role, who acts named, an unknown or capability-bearing tool, its arguments, the router's own — is an in-band tool error (`isError`) carrying the reply the route would give. Each HTTP body negative has its MCP twin, refused with the same reply (`test_operator_mcp.McpEnvelopeTest`).

**Logging, and what is never repeated** (Astra 1e review finding 3). One line per request — principal (`role:name`, or `-`), method, route, HTTP status, the reply's status — and nothing else: never a header, a token, a query or a body. The method and route are the service's own labels (`label()`): a route it serves by its name, `/v1/commands/?` or `?` otherwise, `GET`/`POST` or `?` — never the request's own text, which may carry a credential. The listener's own diagnostics follow the same rule: a fault behind the service is logged by its type and the same labels; the parser's refusals (an unsupported method, a malformed request line or version, a request line or header too long) are fixed JSON replies with the standard reason phrase and one fixed log line, instead of http.server's page repeating the request; a connection fault is one line naming its type, not socketserver's traceback. And every reply and log line passes `Credentials.redact()`, which takes each configured token out wherever it stands — so a refusal that echoes a body's key cannot reflect one — in each form a reply can carry it: as it is or JSON-escaped (replaced where it stands), percent-encoded or as a number's digits (the string or number replaced whole). A tool's reply over MCP is redacted before it is nested as the tool's text, where JSON escaping would otherwise hide a token holding `"` or `\` from the outer pass; and an MCP id carrying a configured token in any of those forms is refused as an invalid request (-32600) answered with a null id, nothing dispatched — echoing it would repeat the credential, replacing it would answer with another id (Astra 1e-repair re-review finding 2). (An unknown string in an authenticated operator's own body is not a credential the engine can know; it is echoed only to that operator, in a refusal's detail.) The engine logs its principals at start as `role:name`.

## Status (`status.py`; INVARIANTS RG-9, H-4)

The router's `status` read (`gen2/router/status.py`) gives the committed rows in one snapshot and its own judgments of them now; the station's incidents come from `Supervisor.incidents()` (the jobs directory). Each topic and each live invocation carries `waiting`, a list of reasons, each read off a fact:

- **Topic**: its status's own (`brief_confirmation`, `scoping_report`, `scope_approval`, `contract_approval`, `claim`, `held`, `capability_blocked`, `stopped_for_resources`, `judgment`; an active topic's work is in its invocations, a completed or retired one waits for nothing); `paused`; each open `hold` (class, cause, owner, deadline, required authority, what clears it, whether its deadline passed); each `brief_awaiting_confirmation` (owner, review deadline, overdue); each `draft_awaiting_approval` an approval could still approve; each lane whose last work ended failed or cancelled: `requeue` (none yet), `retry_claim` (re-queued, not yet claimed) or `requeue_hold` (its exhausted budget's operator hold); `signals` pending; each open `review`; each `incident` of its ended work.
- **Invocation**: the next step of its state (`launch`, `start`, `end`, `commit`, `reconciliation` with its episode, since, and the episode's hold with owner and deadline); `launch_refused` (the router's launch-admission check now); `cancellation` (requested, by whom, not yet confirmed); `deadline_passed`; `lease_expired`; `amendment_pending` (its pins' standing and what superseded them — exactly when its commit would be refused as that); each `incident`, blocking or not — the collected end whose descendants were never confirmed ended stalls as `outcome_unknown_unresolved`, which needs the operator, and an exhausted retry budget is `retry_exhausted`.
- **Engine-wide**: every open incident — its owner, deadline, invocation and topic, the topic from the job's durable order, whatever the topic's lanes have done since (a re-queued and replaced invocation's incident keeps its topic, and in a topic-filtered view every other topic's incident keeps its own; Astra 1e review finding 5), and, blocking, what clears it (`clears_when`: `recover_incident`); an operator recovery not yet finished is listed as its incident with `recovery` (Astra 1e-repair re-review finding 1) — the active config bundle and each bundle live work is pinned to, and the current capability facts (a refused config bundle's `config-bundle` fact included); and the engine's own `waiting`: each open hold of no topic (task 1f: a capability's hold, owned by the operator, bound to its `provider-auth:<provider>` fact, cleared by `hold_clearance`).

Reading status changes nothing: the router's read writes no row, audit events included, and the journals are only read (`test_operator_status.ReadOnlyTest`).

## Recovering a stalled job (`recover_incident`; Astra 1e review finding 2)

The carried 1c ruling: a collected end whose descendants were never confirmed ended stalls as `outcome_unknown_unresolved`; ending the processes and calling `recover()` stalls again at once, because the retained unconfirmed observation is what the job holds. The trusted route is fresh termination evidence → the episode reconciled → recovery. `POST /v1/commands/recover_incident` with `{"invocation_id", "incident_since", "reason"}` — the invocation and the open incident status shows for it — asks the station for exactly that (`gen2/supervisor/supervisor.py` `Supervisor.recover_incident`):

- It is the operator's (403 for the exporter, 401 without a token); `requested_by` is the principal's name, and a body naming it or a `capability_id` is refused (400). No capability is taken from the request and no hold is cleared by it: the operator asks for the station's work, and the router judges what that work produces.
- Under the job's lock, drawing one attempt of the job's recovery budget, as `recover()` does and refilling nothing. With the budget spent it is refused (`recovery_exhausted`) and nothing is signalled.
- Where the retained end's descendants are unconfirmed, the station ends the job's owned execution group afresh and keeps what it found beside the retained end (`collected.rehandled`); the retained observation, its execution record and its bytes in the spool stay as they were. Still not confirmed empty: refused (`termination_unconfirmed`), the incident open as raised, the episode's hold and the lease held.
- Otherwise the incident is closed and the job advanced: the `outcome_unknown` episode is reconciled through the router's `reconcile` under the invocation's capability, with a fresh execution record of that handling — the only way the episode's hold clears (Astra 1c review A7), and capacity is released only then. The reply (`resumed`) names the incident, the fresh termination and where the job got to.
- Recorded unfinished before any of that is done, in the same journal write that draws its allowance (`recovering`: the incident, who asked and why, the fresh termination once made), and recorded finished (`recoveries`, with where the job got to) only once the work is done (Astra 1e-repair re-review finding 1). A recovery cut short — the reply lost, the engine ended or replaced mid-way — is carried on from where the journal stands by the next caller holding the job's lock: the same request again (to a replacement engine too), or the supervisor's own `advance()`/`recover()`; none draws a second allowance, and it answers `resumed` only once the work is done. Until then status lists it as its incident, blocking, with `recovery: {"status": "unfinished", ...}` and `clears_when: recover_incident`.
- Keyed by the incident: the same request once its recovery is finished replays it; a request naming another incident, an unknown job, or a request not of this shape is refused with nothing done (an unfinished recovery of another incident is finished first). Every attempt is recorded in the job's journal (`recoveries`).

Other incidents (an outage, a failing write, a refused lifecycle write) are recovered the same way, without the fresh termination: the incident closed on budget, the job advanced. The autonomous scheduler loop that would drive the supervisor is still Phase 2; this is the operator's manual route, which does not wait for it.

## Not here, and structural limits

- **TLS** is not built: the listener is published on host loopback only. MCP is the stateless subset above (tools only: no resources, prompts, sessions or streaming).
- **The CLI's exit classes.** 0: the engine answered and the operation did not refuse. 1: it refused (the reply's `status` is `refused` or `rejected`). 2: no usable answer — the engine unreachable; its reply cut short, not HTTP, or not a JSON object with a status (every `http.client` protocol error, `IncompleteRead` included, is this; Astra 1e review finding 6); or the transport refused the request (401, 403, 404, 400, 411, 413, 5xx). After a command whose reply was lost or cut short its outcome is unknown; nothing is retried, and running it again replays under its key.
- **A body answered unread** (Astra 1e review finding 8). The service refuses before it parses: a missing or wrong token (401), a route or role it does not serve (404, 403), an over-long declaration (413). After that answer the listener reads and throws away the rest of a declared body only if it is at most 64 KiB, only while each next byte comes within 1 s (an idle timeout), and only for 2 s in all — so a client still sending a small body completes its send and the connection closes cleanly, rather than being reset with its answer lost. Past any of those bounds nothing is waited for: the connection closes, and a client still sending may see its send fail after the whole answer was sent. Nothing discarded is looked at (`test_operator_auth.UnreadBodyTest`: the review's fragmented client, both sides of the ceiling, a client too slow, no body).
- **Tokens live in the engine's environment.** A process running as the same OS user can read another's environment (`/proc/<pid>/environ`); agents get a scrubbed environment (`gen2/supervisor/jobshim.py`), but keeping them from the engine's process is OS-level isolation — another user or container — which is deployment's.
- **The router trusts the surface's names.** It records the `operator_id` and `closed_by` it is handed; it does not check a name against the principal set. What makes them authenticated is that only this surface reaches those operations across a process boundary (the composition root wires it; the boundary graph keeps the store the router's).
- **Status holds the write lock while it reads** (one consistent snapshot), so a large status delays writers for its duration. Supervisor incidents are read from the jobs directory beside that snapshot, not inside it.
- **Capability facts are shown, not pushed.** Status lists each current fact with its `since`; the facts are recorded on transitions (H-2), but no alert is sent anywhere: an alerting channel is Phase 3's (projections).
- **One thread owns the router** (`gen2/app/engine.py`): requests are answered one at a time, in arrival order; a request waits at most 60 s for its turn, then gets 500 (health: 503).
